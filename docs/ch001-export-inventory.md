# CH001_export 盤點與完整性驗收

舊 ERP（鼎新 e-Go）的整庫傾印，是自建 ERP 的唯一歷史資料來源。舊系統要退場，
這份匯出不會再更新，所以**讀法必須一次弄對**。本文記錄怎麼讀、驗過什麼、
哪些表對應到 CTOS 的哪裡。

- 來源：`smb://192.168.11.6/d/CH001_export`（唯讀取用）
- 檔案：590 個 `.txt`，其中 **197 個有資料**
- 格式：Big5 系列編碼、`|` 分隔、**無標題列**、`0x00` 表 NULL、CRLF 斷列
- 工具：`scripts/ch001_reader.py`（讀取器）、`ch001_profile.py`（單表剖析）、
  `ch001_inventory.py`（全表盤點）、`ch001_verify.py`（完整性驗收）

## 一、讀法：不能先解碼再切分

Big5 雙位元組字的低位元組範圍是 `0x40-0x7E` 與 `0xA1-0xFE`，**其中 `0x7C` 就是
`|` 本身**。`decode(...).split("|")` 有兩個獨立的壞法：

1. `errors="replace"` 時，任何一個解不開的字會連帶吃掉後面的位元組，分隔符從那裡
   開始全部錯位。實測 `KJSNHB` 有 113 列因此欄數不對，且**不會報錯**。
2. 改用 bytes 直接 `split(b"|")`，低位元組是 `0x7C` 的中文字會被從中間切斷。

正解是**先用狀態機在 bytes 上切欄，再逐欄解碼**（`ch001_reader.split_row`）。

改用正確切法後的實測差異：

| 表 | 舊法異常列 | 新法異常列 |
|---|---:|---:|
| `KJSNHB` | 113 | **0** |
| `JSKJDB` | 12 | **2** |
| `TPADGA` | 3 | **0** |
| `DCSIAB` | 3 | **0** |
| `TPADFA`／`CRMIKG` | 各 1 | **0** |

### 編碼

197 張表裡 `big5` 解得開 176 張、`cp950` 5 張、`big5hkscs` 10 張。另有 6 張
三種都解不開：客戶主檔 `TPADFA`、聯絡人 `CRMIKG`、銷貨單 `JSKKEA`／`JSKKEB`、
報價單 `DCSIAA`／`DCSIAB`。原因是舊系統造字（Big5 使用者造字區 `0x8140-0xA0FE`），
全檔共 42 處，位元組為 `81a7`／`8168`／`836a`。

造字**不靜默丟棄**，落到 Unicode 私用區佔位；要還原字形得跟原系統要造字檔。

## 二、完整性驗收

`scripts/ch001_verify.py --src <目錄>`，五項全過。最強的一項是借貸平衡 ——
少一筆分錄就不可能平：

```
分錄 319,121 筆，無法解析 0
傳票 118,946 張，平衡 118,946（100.0000%），不平衡 0
借方合計 8,502,130,448.00　貸方合計 8,502,130,448.00　差額 0.00
```

另外：進貨／銷貨／傳票／付款四張表 **2007–2026 一年不缺**；主要單據的單頭明細
孤兒率接近 0。**結論：來源完整，可以據以自建。**

### 分錄表是 `KJSNHB`，不是 `KJSNFB`

資料字典把兩張都列在「會計傳票」下，但兩者不同：

- `KJSNFB`（303,945 列）是單邊表示：第 8 欄借貸號（`1`／`-1`）乘第 9 欄金額，
  這樣只平 **87.24%**。
- `KJSNHB`（319,121 列）是**借方貸方分兩欄**（第 8／第 9 欄），平 **100%**。

匯入要用 `KJSNHB`。字典另外列了 `KJSNIB`／`KJSNJB`／`KJSNKB` 但檔案不存在；
既然 `KJSNHB` 已 100% 平衡，那三張是輔助表，不影響查帳。

## 三、已知瑕疵（匯入器要處理，不可靜默丟）

| 瑕疵 | 筆數 | 說明 |
|---|---:|---|
| 會計傳票分錄無單頭 | 2 | 類別 `2`，二十年來 2 筆 |
| 會計傳票單頭無分錄 | 1 | 類別 `2` |
| `JSKJDA` 第 1 列是殘列 | 1 | 無單號、無廠商、無日期，數值欄全為 0，只有建檔 2007-06-11 與異動 2008-12-08 兩個時間戳。舊系統誤建後清空但沒刪除 |
| `TPABYA` 等欄數不一 | — | **不是資料表**，是系統的查詢定義（`<TPA><SQL><![CDATA[...`），含多行 SQL。不進 `ch001` |

### 曾經誤判為瑕疵、實為讀法問題的兩件

早期版本的讀取器假設 CRLF 一律是列尾，但**欄位內容可以含換行**，於是一列被切成兩段：

- 進貨明細有一筆品名裡有 CRLF，整列被切成 4 欄與 60 欄，害那張單的明細加總短少 6,000。
- 銷貨明細那筆「單號欄被打成中文備註」也是同一個原因，不是有人打錯。

`ch001_reader.read()` 現在會把欄數不足的段落與下一段接回去（接回時補回被切掉的
CRLF，內容無損）。修正後進貨、銷貨、採購、報價四組單據的單頭明細孤兒全部歸零。

## 四、與 ERPNext 匯出的關係

兩份資料互補，不是二選一（ERPNext 匯出見 `docs/erpnext-backup.md`）：

| | ERPNext | CH001_export |
|---|---:|---:|
| 客戶 | 419 | 440 |
| 廠商 | 665 | 673 |
| 聯絡人 | 951 | 3,455 |
| **商品** | **118** | **25,159** |
| 進貨 | 17 張 | 47,276 |
| 銷貨 | 1 張 | 17,649 |
| 專案 | 10 | **無此表** |

**合併的 key 是現成的**：97.3% 的 ERPNext 廠商名稱開頭就是舊系統代號
（格式 `SX0001 - 名稱`，647/665 對得上 `TPADGA` 第 1 欄）。所以 `source_ref`
用舊代號，先灌 CH001 再灌 ERPNext 不會產生重複。

另兩個交叉驗證的結果：`TPADGA` 第 5 欄與 ERPNext `tax_id` 命中 91.5%（確認是統編）；
現有的 `normalize_party_name`（`scripts/erpnext_import.py`）對廠商全名命中 96.7%，
不必改寫。

專案只有 ERPNext 有（`TPADKA` 無資料），商品單位換算 `TPADEB`、客戶分類 `TPADFC`
也都沒有匯出檔。
